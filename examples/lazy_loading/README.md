## The Power Of Laziness

"Many" security practitioners believe that the fewer sections of memory of a running process marked as RW, the better.
And I see no reason to disagree. However, when a process is not compiled in "the right" way, the dynamic linker and the
operating system have a hard time marking sections of memory of a running process RO.

Why is that?

A dynamically linked executable is usually compiled in such a way that its use of functions from shared libraries is done
through indirection. The indirection is necessary because

a. The compiler gets a single chance to emit code transferring program control to a function defined in a shared library, but
b. The operating system is free to load the definition of that function any place that it likes (and it may even load it in
different places every time the program is executed).

The indirection generated by the compiler for each shared library consists of a small bit of trampoline code whose structure is
known by the dynamic loader. The trampoline code is designed so that the first time it is executed, a unique ID for each shared
library function is put on the stack and control is transferred to the dynamic linker. The dynamic linker will load the required
library _and update the trampoline so that future invocations of the shared library function will not invoke the loader again_.

The update requires a change to the section of memory of the running process that stores executable code. As a result, for a
dynamically linked executable whose shared libraries are loaded the first time they are used, the section of memory of the running
process that stores executable code cannot be marked RO!

> Note: For a more in-depth analysis of this process, head over to [this mini assignment](https://github.com/hawkinsw/CS5138/tree/main/MiniAssignmentExplore).

The solution is relatively straightforward: Direct the operating system to load all the shared libraries (and do all the updates)
before the program begins execution. Once everything is updated, no future changes to the sections of the program's executable code
will be necessary -- that section can be marked RO!

Many Linux distributions compile the programs that they ship so that they load all their shared libraries before program execution begins.
For instance, [Ubuntu does it](https://wiki.ubuntu.com/ToolChain/CompilerFlags) and so does [NixOS](https://nixos.org/manual/nixpkgs/stable/#bindnow).

Unfortunately, there is one small problem: startup time! For a program that loads lots of shared libraries, doing all these loads
before the program even starts could increase the amount of time it takes a program to start! See [below](#time-is-of-the-essence)
for some rough estimates of the overhead!

When you are setting the flags for your compilation and linking and for programs you write, you can instruct the _linker_ to perform
lazy or strict loading, use the `now` and `lazy` flags. For an example of how to set those flags for targets in CMake, see the
`CMakeLists.txt` file and the using the `target_link_options` function.

### Time Is Of The Essence

To see just how much of an impact loading all the functionality from shared libraries that a program needs _before_
it can begin, the dynamic linker gives us a pretty powerful tool!

If you set the `LD_DEBUG` environment variable to `statistics`, the dynamic linker will output a cool set of diagnostic
information. Using it on `lazy` and `now` gives output that looks something like 


